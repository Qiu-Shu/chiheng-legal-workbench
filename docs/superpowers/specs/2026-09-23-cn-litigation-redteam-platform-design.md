# 持衡·中国诉讼攻防审查平台设计规格

- 文档版本：1.0-draft
- 基准日期：2026-09-23
- 项目目录：`work/cn-legal-review`
- 当前状态：已完成交互式设计确认，待用户审阅本规格后进入实施计划阶段
- 既有成果：P1 中国本地化 Skill、静态测试、发布说明与压缩包

## 1. 目标与已确认决策

本项目把现有 `cn-litigation-redteam` 建设为可供中国大陆律所真实使用的诉讼攻防审查系统。系统同时服务本机 Codex 工作台与 ChatGPT 私有 Plugin 入口，共用同一套核心 Skill、公共法律资料、检索服务和质控规则。

已确认的关键决策如下：

1. 业务范围面向中国大陆全领域法律工作，不把吉林、长春、松原误写成唯一适用地域；地方资料建设优先从吉林省、长春市、松原市开始。
2. 全国全领域统一建设来源与数据底座，各领域逐步验收。未经充分验收不降低输出内容和分析深度，只在文末标示版本状态；具体来源冲突、时效不明或材料不足仍须在相关结论旁提示。
3. 公共法律资料、商业尽调资料、客户案件资料和项目治理记忆相互隔离。
4. Scrapling 先安装并完成合规烟雾测试，再进入来源采集；它只能执行被允许的访问，不能创造授权。
5. 官方来源为第一顺位，依法授权的商业 API/MCP 为补充来源，网页会员采用人工查询和官方导出导入，不以爬虫代替正式接口授权。
6. 本机服务使用 macOS `launchd` 自动启动、异常自动重启、健康检查和离线降级；仅监听本机回环地址。
7. ChatGPT 侧采用私有 Plugin 入口，暂不公开发布；旧式自定义 GPT 不是唯一或核心依赖。
8. Obsidian 只保存项目决策、索引、覆盖状态、验收记录和更新日志，不保存法规全文、会员凭证或案件原始材料。
9. 数据更新采用增量抓取、隔离区校验、审核后发布、旧版本保留和可回滚策略。
10. “全面”定义为覆盖状态可审计、关键问题可检索、已知缺口可见，不以抓取文件数或不可验证的“绝对无遗漏”承诺替代质量证明。

## 2. 设计原则与边界

### 2.1 设计原则

- **权威优先：**法律命题优先绑定发布机关的具体原文、条款或裁判页面。
- **时点明确：**法规、司法解释、地方规范和案例均记录版本、效力期间、地域和检索日期。
- **证据可追溯：**每个关键结论能够回到来源记录和原文片段。
- **正反核验：**检索支持己方结论的依据，也检索例外、相反依据、废止信息和程序障碍。
- **身份可靠：**企业和自然人同名不得自动合并；优先使用统一社会信用代码、身份证明字段或其他可靠标识。
- **数据最小化：**公共数据库不接收客户秘密、非公开案卷、账户凭证或不必要的个人信息。
- **人工签发：**系统可以生成完整拟稿，但不得代替律师对事实承认、权利处分、期限、诉讼请求和最终签发的责任。
- **诚实降级：**来源失败、数据冲突或未完成核验时降低结论确定性，不把失败伪装成“未发现”。

### 2.2 不在本项目范围内的行为

- 自动立案、自动提交法院、自动发送律师函或联系相对方；
- 自动作出事实承认、和解承诺、诉讼请求变更或权利放弃；
- 绕过登录、验证码、付费墙、访问频控、`robots.txt` 或其他技术限制；
- 镜像企查查、天眼查等商业平台的会员数据库；
- 将客户案件资料混入公共法律知识库；
- 用文件数量、抓取数量或模型自信度宣称已覆盖全国全部法律资料；
- 在完成私有验收前公开发布 Plugin 或向不受控用户提供服务。

                        │          │
                 ┌──────┴──────────┴───────┐

                 └────────────▲────────────┘
                              │
                 ┌────────────┴────────────┐
                 │ Scrapling 受控采集/导入器 │
                 └────────────▲────────────┘

          │ 官方公开网站       │ 正式 API/MCP        │ 人工导出文件

旁路隔离：
- 案件私有层：每案独立目录、授权边界、审计记录，不进入公共数据库。

入口、业务规则、检索服务和数据存储解耦。更换 ChatGPT 或 Codex 入口时，不重建核心法律能力；更换商业供应商时，也不修改诉讼审查方法。

## 4. 核心组件

### 4.1 中国诉讼攻防 Skill

保留原技能的三遍审查：候选攻击、可持续性过滤、重建成稿；增加中国法下的程序路由、证明责任、事实自认、时效、地域和来源检查。

支持两个明确模式：

- `attack_opponent`：攻击对方文书，不为对方补造其未提出的事实。
- `stress_test_own`：压力测试己方文书，允许构造与现有材料和法律相容的最强反方回应，并提出修复建议。

默认交付内部审查表和拟对外稿。两个文件必须隔离，内部策略、未核验假说和私人检索日志不得混入拟对外稿。

### 4.2 来源注册与覆盖审计

来源注册表至少记录：

- 来源 ID、名称、主管或发布主体；
- 全国/地方/商业属性；
- 覆盖地域、法律领域、程序类型和资料类型；
- 官方原文、官方转载、解读、案例、商业聚合等来源层级；
- 访问方式：公开页面、静态文件、动态渲染、API、MCP、人工导入；
- 授权状态、自动化许可状态和访问限制；
- 更新计划、最后尝试时间、最后成功时间；
- 解析器版本、内容哈希、失败原因和人工负责人。

覆盖状态按“领域 × 程序 × 地域 × 时间”计算，阶段使用：

`source_listed → fulltext_acquired → versioned → retrievable → scenario_passed → lawyer_reviewed`

系统不得把 `source_listed` 或仅有首页链接解释为“已覆盖”。

### 4.3 公共法律数据库

使用 SQLite 作为真实数据存储，FTS5 作为第一阶段全文检索。暂不引入向量数据库；只有经过检索评测证明精确检索和同义词扩展仍不能满足需要时才评估增加语义检索。

数据库保存：

- 法律、行政法规、司法解释、部门规章、地方性法规、地方政府规章及合规纳入的规范性文件；
- 指导性案例、人民法院案例库参考案例、典型案例、司法裁判和其他合规公开案例；
- 发布、修改、废止、失效和参照状态变化记录；
- 原始快照、标准化文本、段落或条款片段、来源定位和内容哈希；
- 抓取、校验、审核、发布和回滚日志。

### 4.4 企业与执行尽调层

该层与法规案例库分开，支持：

- 企业登记、历史变更、股东和主要人员；
- 司法案件、被执行、失信、限制高消费、终本、破产和公告；
- 行政许可、行政处罚、经营异常、严重违法失信；
- 知识产权、招投标、资质及必要的公开经营风险；
- 关系路径和主体匹配置信度。

官方基础来源包括国家企业信用信息公示系统、中国执行信息公开网、信用中国、人民法院公开数据库、破产及公告平台、知识产权主管机关和地方市场监管部门。企查查、天眼查、元典、北大法宝等仅按授权作为补充来源。

### 4.5 本地检索 MCP/API

提供窄而稳定的工具接口，至少包括：

- 查询现行或历史版本法规；
- 按条款、案由、程序、地域和时点检索；
- 查询案例参照状态与裁判效力；
- 根据统一社会信用代码或其他标识查询企业和风险事件；
- 返回来源片段、定位、抓取时间、审核状态和覆盖警告；
- 查询来源健康、更新状态与覆盖缺口。

每次工具返回都携带结构化来源元数据。入口不得只接收一段没有出处的合成答案。

## 5. 数据分层与隔离

### 5.1 四类数据

|数据层|内容|允许进入公共索引|典型保留策略|
|---|---|---:|---|
|公共法律资料|官方公开法规、案例、公告和规范|是|按版本长期保存|
|授权商业资料|正式 API/MCP 返回或授权导出内容|依合同决定|按许可期限和字段范围|
|案件私有资料|案卷、证据、客户身份和律师工作成果|否|按案件与律所制度|
|治理记忆|决策、来源目录、覆盖、测试和更新日志|否|项目生命周期内保留|

### 5.2 原始区、隔离区和发布区

```text
原始快照 raw
  → 隔离区 quarantine
      → 结构、哈希、来源、版本、地域、时效校验
          → 人工或规则批准
              → 发布区 published
                  → SQLite/FTS5 可查询索引
```

新增资料不得从网络响应直接进入生产索引。失败或可疑资料保留在隔离区并写明原因，不覆盖最后已知良好版本。

## 6. 核心数据模型

### 6.1 规范文件

- `law_id`：同一规范文件的稳定标识；
- `version_id`：每次公布、修改、修订或状态变化的版本；
- `fragment_id`：条、款、项、目或可稳定引用的段落；
- `issuer`、`document_number`、`authority_level`；
- `published_at`、`effective_from`、`effective_to`；
- `territorial_scope`、`subject_scope`、`procedure_scope`；
- `status`：草案、现行、已修改、废止、失效、未知；
- `source_id`、`source_url`、`locator`、`content_hash`；
- `review_status`、`reviewed_at`、`reviewed_by`。

### 6.2 案例

案例必须分开记录：

- `reference_status`：指导性、参考、典型、普通公开裁判、不再参照等；
- `judgment_validity`：裁判本身是否被撤销、改判或存在其他已知效力变化；
- `court`、`case_number`、`decision_date`、`cause_of_action`；
- `procedural_stage`、`region`、`key_holding`；
- `source_id`、`source_url`、`locator`、`content_hash`。

“不再参照”不得自动等同于“原裁判无效”。

### 6.3 企业、主体与风险事件

- `entity_id`、统一社会信用代码、名称和历史名称；
- 主体类型、登记机关、登记状态；
- 人员、股权和控制关系及有效期间；
- `risk_event_id`、风险类型、发生时间、公开时间和当前状态；
- 来源记录、查询时间、授权通道和原始定位；
- 身份匹配字段、匹配方法和置信度；
- 查询目的、案件 ID（仅作受控引用）和审计日志。

同名企业或同名自然人不得仅凭名称自动合并。

## 7. 来源优先级与准入规则

默认优先级：

1. 发布机关或法定公示机关的具体原文；
2. 其他官方机关的可核验转载；
3. 正式授权、能够保留来源字段的商业 API/MCP；
4. 依法取得的商业平台官方导出报告；
5. 权威出版物、专业机构解读或新闻，仅作发现线索或背景材料。

关键法律命题必须尽量回到第一顺位来源。商业平台的风险标签不能直接替代原始登记、公示、执行或裁判记录。

准入时检查：发布主体、内容完整性、时效、地域、文件层级、引用定位、访问与存储授权、个人信息最小化、版权和再利用限制。

## 8. Scrapling 使用边界

### 8.1 可以执行

- 读取允许自动访问的公开法律、法院、政府和地方机关网页；
- 在必要时处理公开动态页面；
- 保存原始响应、最终 URL、时间、状态码、内容哈希和解析结果；
- 按来源配置限速、重试、条件请求和增量更新；
- 将失败页面送入人工处理队列。

### 8.2 不可以执行

- 绕过账号登录、验证码、付费墙或访问控制；
- 模拟或破解反爬机制以取得平台未授权的数据；
- 使用网页会员会话批量抓取商业数据库；
- 在收到 403、验证码、明确拒绝或高频限制后继续升级对抗；
- 把一次成功读取夸大为可持续、完整或合法授权的采集能力。

### 8.3 失败策略

- 普通网络失败最多自动重试两次，并采用退避；
- 遇到 429 尊重服务端等待要求，不并发施压；
- 遇到 401、403、验证码、登录墙或条款限制立即停止自动化；
- 保留最后已知良好版本，记录新鲜度下降；
- 对关键来源创建人工核验任务或切换到官方备用渠道；
- 补采成功前，不把“本次未取到”表述成“没有该资料”。

## 9. 企查查、天眼查及商业来源

### 9.1 网页会员模式

网页会员用于律师人工查询和平台允许的官方导出。Skill 可以解析用户合法取得的报告、表格或页面导出，但不得后台批量爬取会员页面，也不得收集密码、短信验证码、会话 Cookie。

用户对本项目的授权不替代商业平台的许可。天眼查现行用户协议明确限制使用爬虫、机器人等自动化手段获取数据，并限制不合理高频、批量抓取。企查查面向自动接入提供独立的开放平台 API/MCP、Key、额度和 IP 白名单机制。

### 9.2 正式 API/MCP 模式

开通正式接口后才启用自动调用：

- 密钥存入 macOS Keychain 或本机受限环境配置，不写入 Skill、数据库、日志或 Obsidian；
- 按购买字段、用途、地域、频率、调用次数和存储期限使用；
- 保存调用时间、接口代码、查询主体、返回字段范围和授权版本；
- 自动调用失败时回退到官方公开来源或人工导出流程；
- 不将商业数据用于超出合同范围的训练、数据挖掘或对外再分发。

### 9.3 案件中的调用次序

1. 先查官方工商、执行、信用、法院等来源；
2. 判断主体是否唯一匹配；
3. 如有正式商业 API/MCP，自动补充关系和历史风险；
4. 只有网页会员时，提示律师人工查询并导出；
5. 将商业结果与官方原始记录交叉核验；
6. 输出来源、查询时间、匹配依据、未核验项和法律意义。

## 10. 检索与自动调用策略

### 10.1 强制检索触发条件

下列情况必须调用本地法律检索服务：

- 输出承担结论作用的现行法、司法解释或地方规则；
- 判断期限、管辖、证明责任、请求权基础或程序救济；
- 援引案例支持类案论证；
- 企业主体、执行、失信、限高、破产或工商信息影响案件策略；
- 用户要求核验截至特定日期的法律状态。

### 10.2 不自动外发案件秘密

检索查询优先使用抽象法律问题和公开主体标识。客户私密事实、证据全文、身份证号、联系方式和未公开争议细节不得发送到公共来源或商业接口，除非存在明确、必要且经授权的业务依据。

### 10.3 检索结果要求

每个承担结论作用的依据至少包含：标题、发布主体、版本或日期、具体条款/段落、地域与效力状态、来源链接或本地快照定位、检索时间。仅返回数据库首页或搜索结果列表不构成核验完成。

## 11. 运行服务、自动启动与更新计划

### 11.1 本机服务

使用 macOS `launchd` 管理：

- 法律检索 MCP/API；
- 更新调度器；
- 健康检查和失败重启；
- 必要的来源采集工作进程。

服务仅监听 `127.0.0.1` 或本机 Unix socket。开机或用户登录后自动启动，异常退出自动重启；健康检查不自动修改数据。

### 11.2 更新频率

- 每次真实任务：即时核验本次承担结论作用的依据；
- 工作日 06:30：全国来源增量更新；
- 每周二、周五 07:00：吉林、长春、松原地方来源更新；
- 每周日 08:00：完整性、索引、哈希和版本关系检查；
- 每月第一个周日：生成领域、程序、地域、时间覆盖缺口报告；
- 重大立法、司法解释或指导性案例状态变化：人工触发紧急更新。

错过计划任务时只进行一次补跑，避免积压任务并发冲击来源。

### 11.3 发布流程

自动抓取只进入隔离区。结构校验、来源校验、差异检查和必要人工审核完成后，才提升为发布版本并重建查询索引。发布失败时继续使用上一良好版本。

## 12. ChatGPT 私有 Plugin 与 Codex 入口

### 12.1 共用能力

Codex 和 ChatGPT Plugin 引用同一核心 Skill 规范与本地 MCP 工具契约。入口层只负责会话、文件接收、工具调用和结果展示，不复制一套不同的法律规则。

### 12.2 私有 Plugin

Plugin 包含：

- `.codex-plugin/plugin.json`；
- `skills/cn-litigation-redteam/`；
- 本地 MCP 连接配置和健康检查说明；
- 用途说明、数据边界、快捷提问和安装文档。

第一阶段只在用户自己的 ChatGPT/Codex 环境私有使用，不提交公共市场。若本地 MCP 不可达，Plugin 明确显示离线状态，并允许基于用户提供材料生成完整分析，但不得伪造已经完成的在线核验。

### 12.3 建议快捷入口

- 审查对方起诉状、答辩状或代理意见；
- 压力测试己方拟提交文书；
- 核验法律依据、案例和程序路径；
- 对企业、关联方和执行风险进行案件尽调。

## 13. 输出、版本和律师审批

### 13.1 三个发布状态

`实验版`、`律所试用版`、`生产版`使用完全相同的分析流程、检索规则、输出结构、详细程度和语言质量。版本状态不删除内容、不缩短意见，也不把实验版降为只能提供提纲。

差异只体现在：

- 该领域已经通过何种测试和律师验收；
- 文末固定版本提示；
- 后台覆盖与验收记录。

具体结论若存在来源冲突、时效不明、事实不足或检索失败，必须在相关结论附近标注。这属于案件实质信息，不属于版本提示。

### 13.2 固定文末提示

**实验版：**

> 本报告由实验版系统生成，分析方法和输出标准与生产版一致，但相关领域的数据覆盖、检索效果或行为规则尚未完成全部验收。对外使用前，应由承办律师依据案件原始材料、现行有效法律及官方来源逐项复核。

**律所试用版：**

> 本报告由律所试用版系统生成，分析方法和输出标准与生产版一致，已完成基础测试，但相关领域尚未完成全部律师验收。任何诉讼主张、事实承认、权利处分、期限判断和正式文书均须经承办律师复核签发。

**生产版：**

> 本报告由已经通过对应领域验收的生产版系统生成。系统输出不替代承办律师对案件事实、证据原件、法律时效、程序期限及最终诉讼策略的专业判断与签发责任。

### 13.3 强制人工审批点

无论版本状态，以下事项均须律师审批：

- 新增或改变事实承认；
- 放弃、变更诉讼请求或实体权利；
- 管辖、期限、举证责任和证明标准的决定性判断；
- 赔偿、利息、违约金、费用等关键金额计算；
- 对外文书的署名、签发、提交和发送；
- 使用敏感个人信息或非公开案件资料进行外部查询。

## 14. 错误处理与降级

|故障|系统行为|禁止行为|
|---|---|---|
|来源无法访问|使用上一良好版本，显示新鲜度和失败时间|声称已经实时核验|
|登录/验证码/403|停止自动访问，转人工或授权接口|绕过限制|
|法规版本冲突|并列展示版本及适用时点，要求人工判断|自动选择更“新”的文本|
|主体同名|要求统一社会信用代码或更多身份信息|自动合并风险记录|
|官方与商业数据冲突|保留两者并优先核验官方原始记录|用商业风险标签覆盖官方记录|
|MCP 服务离线|继续基于已提供材料分析并在结论处标识未核验|生成虚假引用|
|索引损坏|切换只读上一索引，暂停新发布|在损坏库上继续写入|
|更新时间错过|补跑一次并记录|并发执行所有积压任务|

严重故障必须进入审计日志，并在恢复后执行完整性校验。

## 15. 安全、隐私和审计

- 服务默认仅本机可访问；远程访问需另行设计认证和网络边界。
- API Key、MCP Token、账号密码和 Cookie 不写入仓库、日志、数据库或 Obsidian。
- 日志默认脱敏，不记录完整身份证号、手机号、住址、银行账号或案卷全文。
- 商业接口查询保存用途和案件关联，但公共库不保存客户案件内容。
- 原始来源快照、标准化文本和发布记录均计算哈希，支持差异检查和回滚。
- 记录采集器版本、解析器版本、审核人、发布时间和被替代版本。
- 导出或删除案件私有材料遵循单案目录和律所制度，不由公共更新任务处理。

## 16. Obsidian 项目记忆

项目记忆结构：

```text
10_Projects/cn-litigation-redteam/
├── Index.md
├── Summary.md
├── Architecture-Decisions.md
├── Source-Catalog.md
├── Coverage-Matrix.md

```

职责：

- `Index.md`：项目目标、路径、当前版本和导航；
- `Summary.md`：极小项目摘要，供记忆钩子按需加载；
- `Architecture-Decisions.md`：已确认选择、原因、替代方案和变更历史；
- `Source-Catalog.md`：来源类型、负责人和状态的索引，不存法规全文；
- `Coverage-Matrix.md`：领域×程序×地域×时间的覆盖阶段；
- `Validation-Log.md`：测试、律师验收、缺陷和发布决定；
- `Updates.md`：法规资料和系统版本更新摘要；
- `Open-Gaps.md`：访问失败、未核验领域和待购买接口。

同时在全局项目登记中记录项目路径。记忆钩子只加载全局核心、项目索引、摘要和最近更新；查询旧资料时先查目录再按需读取，不一次加载整个 Vault。

## 17. 验收与发布门槛

### 17.1 五类验收

1. **来源验收：**主管机关、网址、地域、资料类型、访问方式、授权状态、最后成功时间齐全。
2. **数据验收：**法规版本、效力、地域、条款定位和案例双状态正确；主体身份不误合并。
3. **检索验收：**名称、文号、条号、关键词、同义词、案由、地域和时间查询能够稳定返回具体片段。
4. **行为验收：**既有 50 项场景扩展为可执行回归集，覆盖主要领域、程序、资料不足、自认、引用、冲突和故障降级。
5. **律师验收：**争点、适用法、类案可比性、证据、诉讼价值和对外措辞由真实律师审核，不把同一模型自我检查称为独立律师复核。

### 17.2 量化检查

- 所有承担关键结论的引用均有具体来源和定位；
- 无来源 ID、未批准自认、地域/时点缺失或页码越界时机械检查失败；
- 已发布记录能够追溯到原始快照和内容哈希；
- 新版本索引失败时能够回滚到上一良好版本；
- Plugin 和 Codex 对同一固定测试输入产生等价的检索证据与结构化结论；
- 网页会员凭证、Cookie 和案件隐私不出现在代码、日志、数据库或 Obsidian 中；
- 标记为 `lawyer_reviewed` 的覆盖单元具有真实审核记录。

### 17.3 发布状态含义

- **实验版：**完整功能和完整输出可运行，尚未完成全部系统验收；
- **律所试用版：**基础测试和指定场景通过，处于真实律师受控试用；
- **生产版：**对应覆盖单元已完成规定的自动测试和律师验收。

版本状态是证据化的验收状态，不是能力开关。

## 18. 实施顺序约束

详细任务将在本规格确认后另行编制。实施计划必须遵守以下顺序：

1. 固化现有 P1 基线、目录、依赖和安全边界；
2. 安装 Scrapling 官方 Skill/依赖并完成受控公开页面烟雾测试；
3. 初始化 Obsidian 项目记忆；此后每个阶段同步更新决策、覆盖、测试和缺口；
4. 建立来源注册、授权字段、原始区/隔离区/发布区；
5. 建立 SQLite/FTS5 法律数据模型、版本模型和检索接口；
6. 接入全国官方来源，再接入吉林、长春、松原地方来源；
7. 建设工商、执行与企业尽调层；
8. 接入获正式授权的商业 API/MCP，网页会员保留人工导入；
9. 增加 `launchd` 自动启动、更新调度、健康检查和回滚；
10. 打包本机 Skill 和 ChatGPT 私有 Plugin；
11. 完成自动测试、50 项行为回归、律师验收和分领域发布；
12. 对 Obsidian 项目记忆、安装文档、更新记录和恢复说明进行最终审计。

不得因实施顺序而把未经验证的采集结果直接写入生产库，也不得在 Plugin 可打开后就宣称整个法律数据库已经完成。

## 19. 风险与控制

|风险|控制|
|---|---|
|地方网站不稳定或动态渲染复杂|保留备用官方来源、失败队列、最后良好版本和人工导入|
|法规频繁修改导致旧文本误用|版本化、时点查询、任务级即时核验|
|案例参照状态被误当裁判效力|双字段模型和回归测试|
|商业会员被误当自动化授权|网页会员与 API/MCP 分通道，授权状态进入来源注册|
|全领域目标导致虚假完成感|覆盖矩阵和按单元验收，公开缺口|
|客户材料外泄|案件层隔离、查询抽象化、本机服务和日志脱敏|
|模型生成虚假引用|检索工具返回结构化来源；无来源不得标记为已核验|
|自动更新污染生产索引|隔离区、差异校验、批准发布和回滚|
|实验版被误解为低质量简略版|三个版本同一输出标准，仅验收状态和文末提示不同|

## 20. 设计完成标准

本设计经用户确认后，下一阶段只产出可执行实施计划，不立即把“计划存在”视为系统完成。最终项目完成需要同时满足：

- Skill、数据库、检索服务、更新服务和私有 Plugin 均可在本机运行；
- 自动启动、自动调用、故障降级和回滚经过实测；
- 全国及地方来源状态真实记录，失败和缺口可见；
- 商业数据使用符合授权，网页会员未被用于未授权爬取；
- 50 项以上行为测试和规定的工程测试有真实结果；
- 对应生产领域具有律师验收记录；
- Obsidian 项目记忆能够通过项目索引按需读取；
- 最终交付物包含安装、使用、更新、备份、恢复和卸载说明。
